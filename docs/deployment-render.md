# Deploying GRID-X on Render

> Part of the [GRID-X documentation](README.md). See also [10 — Operations](10-operations.md).

GRID-X ships a Render Blueprint (`render.yaml`) that provisions three resources:

| Resource | Type | Purpose |
| --- | --- | --- |
| `gridx-postgres` | Render PostgreSQL 16 | System of record for the whole platform |
| `gridx-api` | Web service (Node) | NestJS REST API — Swagger at `/api/docs`, health at `/api/health` |
| `gridx-web` | Web service (Node) | Next.js app — marketing site, GRID-X Control, Partner PWA, Inspector |

## 1. Create the blueprint

1. Push this repository to GitHub (already done for `main`).
2. Render dashboard → **New** → **Blueprint** → select the `GRID-X` repository.
3. Render reads `render.yaml` and shows the two services plus the database.
4. Fill in the values Render asks for (everything marked `sync: false`). None of
   them are required for the app to boot except object storage, which is needed
   before drawings or photos can be uploaded — see step 3.
5. **Apply**. The database is created first, then both services build.

The API build runs, in order: install -> build `@gridx/shared` -> generate the
Prisma client and build `@gridx/db` -> build the Nest app. Schema migrations run
in the API service's Render pre-deploy command, where the service can reach the
private Postgres hostname, and therefore still finish before the new version starts.

## 2. Environment variables

Managed automatically by the blueprint:

- `DATABASE_URL` — wired from `gridx-postgres`.
- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` — generated by Render.
- `CORS_ORIGINS`, `WEB_APP_URL` — wired to the web service URL.
- `NEXT_PUBLIC_API_URL` — wired to the API service URL.
- `PORT` — injected by Render and honoured by the API and Next.js.

You must supply in the dashboard:

| Variable | Needed for |
| --- | --- |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` | Drawing, photo and document storage with signed URLs |
| `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD` + `NOTIFY_EMAIL_ENABLED=true` | Email notifications |
| `WHATSAPP_API_URL`, `WHATSAPP_API_TOKEN` + `NOTIFY_WHATSAPP_ENABLED=true` | WhatsApp notifications to partners |
| `IMS_BASE_URL`, `IMS_API_KEY` + `IMS_ENABLED=true` | IMS integration (masters in, status out) |
| `SENTRY_DSN` | Error monitoring |

`NEXT_PUBLIC_API_URL` is resolved to the API service root. If you use a custom
domain for the API, set it explicitly to `https://<api-domain>/api`, because the
API mounts every route under the `api` prefix.

## 3. Object storage

`STORAGE_DRIVER=s3` is the production default: Render instances have ephemeral
filesystems, so `local` storage would lose uploads on every deploy. Any
S3-compatible bucket works (AWS S3, Cloudflare R2, Supabase Storage, GCS with
the S3 interoperability endpoint). Enable versioning and server-side encryption
on the bucket — drawing revision control and the drawing access audit trail
assume objects are never overwritten in place.

## 4. Seeding the first environment

Migrations run on every deploy, but seed data does not. To load roles,
permissions, demo masters and demo users, open a Render shell on `gridx-api` and
run:

```bash
pnpm --filter @gridx/db seed:ci
```

Seeded demo credentials (change them immediately in any real environment):

- internal: `admin@oswar.example` / `GridX@2025!`
- partner: seeded partner phone number / `GridX@2025!`

The seed is idempotent: it upserts roles, permissions and masters.

## 5. Verifying the deploy

```bash
curl https://<api-host>/api/health          # {"status":"ok","database":"up",...}
open https://<api-host>/api/docs            # Swagger UI
open https://<web-host>/                    # marketing homepage
open https://<web-host>/login               # internal login
open https://<web-host>/partner/login       # partner login
```

## 6. Backups and restore

Render PostgreSQL takes daily backups on paid plans. For the production
environment:

1. Confirm the retention window on the database's **Backups** tab.
2. Take a manual backup before any risky migration.
3. Restore procedure: create a new database from a backup, point
   `DATABASE_URL` at it, redeploy `gridx-api`, then verify `/api/health` and the
   quality and finance records, which are append-only by design.

## 7. Scaling notes

- The API is stateless; scale it horizontally on Render. Sessions are JWT-based
  with refresh-token rotation stored in PostgreSQL, so no sticky sessions are
  required.
- Set the database plan by concurrency, not size: the reporting endpoints run
  aggregate queries over jobs, inspections and invoices.
- Move the report catalogue to a read replica if reporting load starts affecting
  transactional latency.
