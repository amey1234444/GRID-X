# 02 — Data model

The schema lives in `packages/db/prisma/schema.prisma`: **78 models and 52 enums**,
implementing the entity list of blueprint Section 11 plus the status workflows of
Sections 5, 8 and 11.

Conventions throughout:

* Primary keys are `cuid()` strings.
* `createdAt` / `updatedAt` on every mutable model.
* Human-facing document numbers (`jobNumber`, `challanNumber`, `invoiceNumber`, …) are
  separate `@unique` columns generated by `SequenceService`.
* Deletes cascade only where a child cannot exist alone (job → milestones, partner →
  capabilities). Financial and quality records are never cascade-deleted from a parent.

### Partner approval workflow

`PARTNER_APPROVAL_TRANSITIONS` in `shared/enums.ts`:

```
DRAFT ──► DOCUMENT_REVIEW ──► CAPABILITY_AUDIT ──► TRIAL_APPROVED ──► APPROVED
                                                                       │
                                                              CERTIFIED ──► STRATEGIC
every state ──► SUSPENDED ──► DOCUMENT_REVIEW | APPROVED
```

Backward moves are allowed one step (a failed audit returns to document review).
`ALLOCATABLE_PARTNER_STATUSES` = `TRIAL_APPROVED`, `APPROVED`, `CERTIFIED`, `STRATEGIC`
— only these may receive a job.

## 3. Components and processes (Module 2)

| Model | Purpose |
| --- | --- |
| `Product` | Finished product, unique on (company, code), `imsRef` links back to IMS |

**Inspection levels**: `LEVEL_1_VISUAL`, `LEVEL_2_SAMPLING`, `LEVEL_3_FULL_DIMENSIONAL`,

## 5. Jobs (Module 4)

`GridJob` is the centre of the system.

| Field group | Fields |
| --- | --- |
| Identity | `jobNumber` (unique), `companyId`, `source` (`SALES_ORDER` / `WORK_ORDER` / `INTERNAL_PRODUCTION` / `REPLENISHMENT` / `MANUAL`), `sourceRef`, `customerProject` |
| What | `productId`, `componentId`, `drawingRevisionId`, `quantity` |
| Quantities | `acceptedQuantity`, `rejectedQuantity`, `reworkQuantity`, `dispatchedQuantity`, `receivedQuantity` |
| Who and when | `partnerId`, `plannedStartDate`, `dueDate`, `acceptedAt`, `declinedAt`/`declineReason`, `productionStartedAt`, `completedAt`, `closedAt` |
| Commercials | `materialResponsibility` (`OSWAR_SUPPLIED` / `PARTNER_SUPPLIED`), `rate` |
| Control | `inspectionPlanId`, `deliveryLocation`, `priority`, `status`, `classAOverrideById` / `classAOverrideReason` |

Supporting models: `GridJobItem` (multi-component jobs), `JobAssignment` (each
allocation with its `recommendationScore` and full `recommendationDetail` JSON),
`JobMilestone`, `JobStatusHistory`, `JobDelay`, `JobClarification`.

### Job status workflow

```
DRAFT ─► AWAITING_PARTNER_ACCEPTANCE ─► ACCEPTED ─► MATERIAL_PENDING ─► MATERIAL_ISSUED
                    │ (declined)                 └──────────────► IN_PRODUCTION ◄──┘
                    ▼                                                    │
                  DRAFT                                    INSPECTION_REQUESTED
                                                                         │
                                                            UNDER_INSPECTION
                                                              │        │       │
                                                          REWORK  QUALITY_  IN_PRODUCTION
                                                              │     ACCEPTED
                                                              └──► INSPECTION_REQUESTED
                                                                        │
                                            DISPATCHED ─► RECEIVED ─► CLOSED
```
Any pre-inspection state may go to `CANCELLED`. `CLOSED` and `CANCELLED` are terminal.

`JobMilestone` carries `clientRequestId` (unique) so an offline replay is idempotent,
plus `syncedFromOffline`, `quantityCompleted`, `expectedCompletionDate` and `isOverdue`.

`JobDelay` records `reason`, `responsibility` (derived from the reason, never
self-reported by the partner), `delayDays`, `expectedCompletionDate` and `resolvedAt`.

## 6. Materials (Module 6)

| Model | Purpose |
| --- | --- |
| `MaterialIssue` | The challan: `challanNumber` unique, job, partner, `status`, `issueDate`, `expectedReturnDate`, `totalIssueWeightKg`, vehicle and driver |
| `MaterialIssueItem` | Per-item lines: `quantity`, `issueWeightKg`, `batchNumber`, `heatNumber`, `theoreticalQuantity` |
| `MaterialReceiptAcknowledgement` | Partner receipt: `receivedWeightKg`, `shortageWeightKg`, `damageRemarks`, `signatureName`, `clientRequestId` (unique, offline-safe) |

| `ScrapReturn` | `scrapWeightKg`, `returnedWeightKg`, `scrapPercent`, challan reference |

`MaterialIssueStatus`: `DRAFT` → `PREPARED` → `ISSUED` → `ACKNOWLEDGED` →

The ten `MaterialTransactionType` values of the blueprint are all present as an enum.

## 7. Quality (Module 8)

| Model | Purpose |
| --- | --- |
| `InspectionPlan` | Per component, with `inspectionType`, `samplingPlan`, `version` |
| `InspectionCharacteristic` | `characteristic`, `specification`, `nominalValue`, `upperTolerance`/`lowerTolerance`, `unit`, `measuringInstrument`, `isCritical` |
| `Inspection` | `inspectionNumber` unique, job, partner, plan, `type`, `status`, `decision`, and the disposition quantities `offeredQuantity` / `inspectedQuantity` / `acceptedQuantity` / `rejectedQuantity` / `reworkQuantity`, requester, inspector, `dueAt` |
| `InspectionResult` | One measured characteristic: `actualValue`, `numericValue`, `verdict`, `sampleNumber`, instrument |
| `NonConformance` | `ncNumber` unique, `defectType`, `quantityAffected`, `probableCause`, `responsibility`, `reworkCost`, `materialLoss`, `customerImpact`, `correctiveActionRequired` |
| `CorrectiveAction` | `caNumber` unique, `stage`, and the 8D-style fields `containment`, `rootCause`, `correctiveAction`, `verification`, owner and due date |
| `ReworkOrder` | `reworkNumber` unique, `quantity`, `instructions`, `status`, `estimatedCost` plus the actuals `completedQuantity`, `scrappedQuantity`, `actualCost`, and `chargeToPartner` |
| `DeviationApproval` | The record behind an `ACCEPTED_WITH_DEVIATION` decision |

**Inspection types**: incoming material, first article, in-process, final, receiving,
partner audit.
**Decisions**: accepted · accepted with deviation · rework required · rejected · hold for
engineering review.
**Corrective action workflow**: `ISSUE_RAISED → CONTAINMENT → ROOT_CAUSE →
CORRECTIVE_ACTION → VERIFICATION → CLOSED` (verification may fall back one stage).

| Model | Purpose |

### Invoice workflow

```
DRAFT ─► RAISED ─► QUANTITY_VERIFIED ─► QUALITY_VERIFIED ─► MATERIAL_RECONCILED
        ─► FINANCE_APPROVED ─► PAYMENT_SCHEDULED ─► PAID
any stage ─► HELD (and back to any verified stage) or REJECTED
```

## 12. Notifications and IMS

`Notification` — per user and channel, with `event`, `title`, `body`, `link`,
`entityType`/`entityId`, `status` (`PENDING`/`SENT`/`FAILED`/`READ`) and `error`.
31 `NotificationEvent` values cover the Section 13 list plus the lifecycle events the
platform generates.

`ImsSyncLog` — every inbound and outbound call: `direction`, `entity`, `recordRef`,
`payload`, `success`, `message`, and for outbound retries `attempts`, `nextAttemptAt`
and `abandonedAt`. Indexed on `(direction, success, nextAttemptAt)` so the retry worker
finds its queue cheaply.

## 14. Migrations

| Migration | Adds |
| --- | --- |
| `0_init` | The full baseline schema (2,312 lines of SQL) |
| `20260817140000_rework_actuals` | Rework actual quantities and cost |
| `20260820120000_scorecard_evidence_totp_ims_retry` | Scorecard sufficiency flags, TOTP columns, IMS retry bookkeeping |
| `20260822090000_incentives_scheduler_locks_distance` | Incentive thresholds, `SchedulerLock`, `RateLimitCounter`, plant/partner coordinates |

CI replays every migration against a clean PostgreSQL 16 and runs
`prisma migrate diff --exit-code` against a shadow database, so a `schema.prisma` edited
without a matching migration fails the build.
